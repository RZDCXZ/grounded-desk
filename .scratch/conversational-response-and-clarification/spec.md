# 交流性回应与澄清提问规格

Status: ready-for-agent

## Problem Statement

访客发送“你好”“谢谢”“你是谁”等非事实性消息时，GroundedDesk 当前仍会执行问题向量化、知识召回与重排；只要没有达到证据阈值，就会把消息处理为可靠拒答，显示“现有知识暂时无法确认”和人工联系入口。类似地，“退款”“价格”等尚未形成完整问题的短输入也会立即被当成知识缺口。

这让助手显得生硬，也会把寒暄、范围外请求和信息不完整的表达错误地写入待解决问题，污染管理员对真实知识缺口的判断。直接降低证据阈值虽然可能减少拒答，但会增加无关内容单元被用于事实回答的风险，破坏 GroundedDesk 的有据回答边界。

## Solution

GroundedDesk 将非事实互动与业务事实问答分开处理。纯问候、致谢、告别、助手身份与能力询问，以及明确超出服务范围的请求，形成使用受控模板的交流性回应；信息不足但已经表达咨询意图的输入，在没有检索到充分证据时形成澄清提问。两者都是独立的会话结果，不附引用、不触发质量反馈或待解决问题，并在访客端显示为普通助手消息。

只要消息包含业务问题，业务问题就优先进入现有知识检索链路。完整业务问题在证据不足时仍然产生可靠拒答；无法确定输入性质时也继续检索，不通过降低重排证据阈值换取更高回答率。同一意图最多连续澄清一次，下一条消息会结合近期上下文重新检索，仍无充分证据时可靠拒答。

## User Stories

1. As a 访客, I want “你好”得到自然的问候回应, so that 助手不会在普通开场时显示知识不足。
2. As a 访客, I want “在吗”得到简短回应, so that 我能确认助手可以继续交流。
3. As a 访客, I want “谢谢”得到礼貌回应, so that 对话可以自然结束或继续。
4. As a 访客, I want “再见”得到告别回应, so that 助手的沟通方式符合日常交流习惯。
5. As a 访客, I want “你是谁”根据助手名称得到回答, so that 我知道当前正在与哪个助手交流。
6. As a 访客, I want “你能做什么”根据助手服务范围得到回答, so that 我知道适合咨询哪些内容。
7. As a 访客, I want 明确超出服务范围的请求得到礼貌引导, so that 我不会看到与真实知识缺口含义不符的警示。
8. As a 访客, I want 助手拒绝自由生成笑话、代码或其他范围外内容, so that 助手仍专注于管理员约定的服务范围。
9. As a 访客, I want “退款”这类残缺输入在证据不足时得到澄清提问, so that 我有机会补充真正想了解的方面。
10. As a 访客, I want 澄清提问引用我刚才表达的主题, so that 我能理解还需要补充什么信息。
11. As a 访客, I want 澄清后的下一条消息结合上一轮上下文重新检索, so that 我不必重复完整问题。
12. As a 访客, I want 同一意图最多连续澄清一次, so that 我不会陷入反复追问但始终得不到结果的循环。
13. As a 访客, I want 澄清后仍无充分证据时看到可靠拒答, so that 我能使用人工联系入口继续处理问题。
14. As a 访客, I want “多少钱？”这类已经完整的问题在无证据时可靠拒答, so that 澄清提问不会掩盖真实知识缺口。
15. As a 访客, I want “你好，请问退款多久到账？”按业务问题处理, so that 问候语不会让事实问题绕过知识检索。
16. As a 访客, I want “谢谢，另外可以开发票吗？”按业务问题处理, so that 礼貌表达不会覆盖消息中的实际问题。
17. As a 访客, I want 有充分证据的简短主题仍能得到有据回答, so that 系统不会仅因输入很短就强制澄清。
18. As a 访客, I want 完整事实问题继续只依据最终证据集回答, so that 放宽交互限制不会降低事实可靠性。
19. As a 访客, I want 交流性回应使用助手配置的语气, so that 非事实互动与助手的业务形象保持一致。
20. As a 访客, I want 明显英文输入得到英文交流性回应, so that 英文对话保持语言一致。
21. As a 访客, I want 中文或中英混合输入默认得到简体中文回应, so that 语言无法确定时仍符合现有产品规则。
22. As a 访客, I want 交流性回应快速返回, so that 简单寒暄不需要等待知识向量化、召回和重排。
23. As a 访客, I want 交流性回应在每日 AI 预算耗尽后仍可使用, so that 不消耗模型的基础互动不会被错误阻断。
24. As a 访客, I want 所有消息仍受每分钟频率限制, so that 公开助手不会因免费模板遭到刷取。
25. As a 访客, I want 交流性消息仍计入会话消息上限, so that 一次会话的长度和上下文规模保持可控。
26. As a 访客, I want 交流性回应和澄清提问显示为普通助手气泡, so that 它们不会被误解为错误或风险警告。
27. As a 访客, I want 交流性回应和澄清提问不显示引用, so that 引用只表示知识来源提供的事实依据。
28. As a 访客, I want 交流性回应和澄清提问不显示人工联系入口, so that 人工升级只出现在真正的可靠拒答或其他既有阻断场景。
29. As a 访客, I want 交流性回应和澄清提问不显示质量反馈按钮, so that 我不会评价一条尚未给出业务答案的中间消息。
30. As a 访客, I want 包含提示词注入或模糊指令的消息在无法确定时继续检索, so that 恶意文字不能借交流性路由绕过事实约束。
31. As an 管理员, I want 寒暄和澄清不创建待解决问题, so that 待解决问题队列只反映真实知识缺口和负面质量反馈。
32. As an 管理员, I want 在会话详情中区分交流性回应、澄清提问、有据回答、可靠拒答和技术故障, so that 我能准确复盘助手行为。
33. As an 管理员, I want 按交流性回应和澄清提问筛选会话, so that 我能检查新路由是否符合预期。
34. As an 管理员, I want 交流性回应和澄清提问不计入有据回答或可靠拒答统计, so that 运营指标保留清晰含义。
35. As an 管理员, I want 概览页暂时不增加低价值的新指标, so that 首版保持信息层级简洁。
36. As an 管理员, I want 后台预览与公开助手使用相同的输入路由规则, so that 发布前预览能够代表真实访客体验。
37. As an 管理员, I want 受控模板只能使用助手名称、服务范围、语言和语气, so that 模板不会制造知识来源中没有的业务承诺。
38. As a 运营者, I want 保留现有重排证据阈值, so that 改善寒暄体验不会扩大无关证据的准入范围。
39. As a 运营者, I want 可靠拒答继续自动进入知识改进闭环, so that 真实知识缺口不会因新路由被遗漏。
40. As a 开发者, I want 交流性回应和澄清提问拥有独立持久化类型, so that API、会话复盘、反馈与统计不需要猜测消息含义。
41. As a 开发者, I want 路由结果由服务端决定, so that 公开客户端不能伪造免费路径或绕过每日 AI 预算。
42. As a 开发者, I want 不确定输入采用“疑则检索”, so that 路由误差优先保持事实安全而不是提高表面回答率。
43. As a 开发者, I want 通过公开会话边界验证行为, so that 测试关注访客可观察结果而不是内部规则实现。
44. As a 开发者, I want 数据库契约明确限制哪些结果可以附引用或接受反馈, so that 新消息类型不会破坏现有数据不变量。
45. As a 开发者, I want 历史会话无需回填或重新分类, so that 功能可以以向前兼容的迁移上线。

## Implementation Decisions

- 遵循 ADR-0005：业务事实必须由内容单元支持；交流性回应和澄清提问不是有据回答，也不是可靠拒答。
- 新增 `conversational_response` 和 `clarification_request` 两种持久化会话结果。现有有据回答、可靠拒答和技术故障语义保持不变。
- 会话完成契约与流式结果必须显式携带最终结果类型，不能再把所有非拒答结果隐式视为有据回答。
- 交流性回应和澄清提问的引用集合必须为空。数据库只允许有据回答保存引用。
- 质量反馈提交契约不接受交流性回应或澄清提问；两种结果均不会触发待解决问题。
- 输入路由由服务端执行，客户端不提交或覆盖路由类别、是否消耗 AI 预算或是否允许澄清等决定。
- 路由优先识别整条消息都是高置信交流性表达的场景，包括问候、致谢、告别、助手身份与能力询问，以及明确超出服务范围的请求。
- 交流性回应使用受控模板，不调用回答生成模型，不自由扩展业务信息。模板只可使用助手名称、服务范围、配置语气和检测到的语言。
- 每个交流类别可提供少量自然但确定性的模板；同一输入和配置应得到稳定结果，便于测试和复盘。
- 只要消息同时包含业务问题，业务问题优先。开头或结尾出现问候、致谢或告别，不得使整条消息绕过检索。
- 无法高置信归类的消息一律进入现有知识检索链路。不得使用大模型自由分类作为首版前置路由，也不得降低重排证据阈值。
- 简短主题或残缺表达先按现有链路检索；检索到充分证据时仍可形成有据回答。只有证据不足且输入明显没有形成完整问题时，才形成澄清提问。
- 已经形成完整事实问题的短输入在证据不足时产生可靠拒答，不以澄清提问代替知识缺口。
- 澄清提问使用受控表达，并以访客当前主题为上下文提示需要补充的信息；不得在澄清文本中加入未经证据支持的条件、选项、数字或承诺。
- 同一对话最多连续出现一次澄清提问。访客下一条消息与近期访客主题及澄清提问共同用于重新检索；仍无充分证据时产生可靠拒答。
- 一个已完成的非澄清结果会重置连续澄清状态。首版不引入独立的长期意图实体或跨会话澄清状态。
- 中文与中英混合消息使用简体中文模板，明显英文消息使用英文模板，沿用现有问题语言检测规则。
- 交流性消息仍创建正常会话与访客消息，并受同一会话并发、每分钟五条和每会话三十条限制。
- 每日成本限制改为只计算会调用 AI 供应商的请求。交流性回应由服务端标记为不消耗 AI 预算；知识检索、有据回答、可靠拒答判定和澄清判定仍消耗预算。
- 预算分类必须在可信服务端完成并通过特权数据库调用传递。过去已经完成的交流性回应不应计入 AI 请求预算，进行中的 AI 请求必须在并发预算检查中占位。
- 交流性回应和澄清提问作为普通助手消息参与会话持久化。近期检索上下文必须保留完成澄清所需的访客主题和澄清提问，但先前助手内容仍不能成为事实证据。
- 访客端和管理员预览端将两种新结果渲染为普通助手气泡，不显示警示卡、引用、人工联系入口、反馈按钮或内部结果标签。
- 可靠拒答继续使用现有警示样式、人工联系入口和待解决问题流程。
- 管理后台会话列表和详情增加两种结果的可读标签与筛选项。两者不合并到有据回答、可靠拒答或技术故障统计中。
- 概览页首版不新增交流性回应或澄清提问指标。
- 历史消息保持原类型，不回填、不推断也不重新分类过去可能由寒暄触发的可靠拒答。
- 所有数据库约束、会话查询、结果筛选、上下文组装、反馈校验和保留策略必须识别新类型，且继续强制组织边界。

## Testing Decisions

- 主要测试接缝是公开助手会话边界：从访客提交消息开始，消费完整流式结果，并核查访客端呈现、持久化结果、引用、反馈可用性、待解决问题和 AI 调用记录。
- 测试只断言用户可观察行为和持久化业务结果，不直接断言内部正则、关键词表、模板选择函数或路由分支。
- 使用现有公开会话端到端测试作为主要先例，继续使用确定性 AI 供应商保证知识检索场景可重复。
- 使用现有公开会话数据库测试作为契约先例，补充新消息类型、完成会话结果、引用限制、反馈限制、待解决问题触发、上下文选择和成本计数。
- 管理后台验证复用通过公开会话产生的数据，在同一端到端工作流中检查列表筛选和详情标签，不单独伪造另一套低层数据。
- 管理员预览至少覆盖一个交流性回应和一个澄清提问，证明预览与公开助手共享相同行为。
- 必须覆盖纯中文问候、英文问候、致谢、告别、身份询问、能力询问和明确范围外请求。
- 必须覆盖混合输入中的业务问题优先，包括问候加问题、致谢加问题和带交流词的提示词注入表达。
- 必须覆盖短主题有证据时形成有据回答、短主题无证据时形成澄清提问、完整短问题无证据时可靠拒答。
- 必须覆盖一次澄清后检索成功，以及一次澄清后仍无证据而可靠拒答；不得出现连续第二次澄清。
- 必须断言交流性回应和澄清提问没有引用、人工联系入口、质量反馈按钮和待解决问题。
- 必须断言可靠拒答仍有人工联系入口并创建待解决问题，有据回答仍保存服务端引用，技术故障仍可重试且不创建知识缺口。
- 必须断言交流性回应不产生 embedding、rerank 或 answer 调用日志，并在每日 AI 预算耗尽时仍可返回。
- 必须断言交流性消息仍受每分钟五条、每会话三十条和同会话单一进行中请求限制。
- 必须断言检索类请求继续受每日 AI 预算限制，且并发请求不能绕过预算占位。
- 必须断言新结果可以被后台会话列表筛选并在详情中正确标识，同时不改变概览页现有指标。
- 回归测试必须确认现有有据回答、可靠拒答、供应商故障、多轮上下文、反馈、待解决问题和会话删除行为继续通过。

## Out of Scope

- 降低或按管理员配置重排证据阈值。
- 使用大模型自由生成寒暄、笑话、代码、天气、生活建议或其他范围外内容。
- 使用大模型作为每条消息的前置意图分类器。
- 构建通用自然语言意图平台、可训练分类器或管理员可编辑关键词系统。
- 在首版支持中文和英文之外的专门交流模板。
- 引入完整国际化框架或翻译管理后台。
- 允许管理员编辑交流性回应或澄清提问模板。
- 对交流性回应和澄清提问收集质量反馈。
- 为交流性回应和澄清提问增加概览指标或新的分析仪表盘。
- 无限澄清、多步骤表单式澄清或跨会话保留澄清状态。
- 重新分类或回填历史会话和历史待解决问题。
- 改变知识来源处理、内容单元形成、向量模型、重排模型、引用上限或人工联系配置。

## Further Notes

- 领域词汇以根目录 `CONTEXT.md` 中的“交流性回应”“澄清提问”“有据回答”和“可靠拒答”为准。
- 设计依据见 ADR-0005“区分非事实交流与有据回答”。
- 可靠性优先级为：明确非事实交流使用受控回应；明确残缺且无证据时澄清；其余情况疑则检索；完整事实问题无证据时可靠拒答。
- 本规格的目标是放宽交互限制，而不是放宽事实证据限制。
- 测试接缝已经确认：公开助手会话为唯一主接缝，数据库仅保留必要契约测试。
