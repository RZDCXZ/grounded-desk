# GroundedDesk MVP 规格

Status: ready-for-agent

## Problem Statement

中小企业运营者希望把公开网站和手工维护的业务知识快速转化为可嵌入网站的 AI 客服，但现有“文档聊天”方案通常只证明模型能够生成文字，无法让运营者确认回答是否有依据、知识更新后是否生效、资料不足时是否会编造，以及真实访客提出的问题能否转化为后续知识改进。

对于首版 GroundedDesk，当前最重要的不是一次性实现完整多租户 SaaS、复杂知识库层级、业务动作或分析平台，而是用最少的核心功能跑通一条真实、可验证的业务闭环：

> 管理员导入知识来源 → 系统完成处理和检索准备 → 管理员预览问答 → 发布助手 → 访客匿名咨询 → 助手给出有据回答或可靠拒答 → 管理员复盘会话并处理待解决问题。

该闭环还必须能在本地开发环境中完整运行和验证。开发阶段使用本地 Supabase，只有当数据库迁移、自动测试、浏览器闭环测试和真实模型冒烟测试全部通过后，才部署到 Supabase Cloud 与 Vercel。

## Solution

GroundedDesk MVP 将提供一个单组织、单管理员、单助手的中文优先 AI 客服产品。管理员通过受限的 Magic Link 进入后台，导入单个公开网页或手工内容，查看处理状态，并使用真实的检索增强生成链路预览回答。

系统使用硅基流动的 `BAAI/bge-m3` 生成向量，在 Supabase Postgres 的 `pgvector` 中召回候选内容单元，再使用 `BAAI/bge-reranker-v2-m3` 重排。证据达到相关性门槛后，DeepSeek `deepseek-v4-flash` 以非思考模式流式生成有据回答；证据不足时，助手可靠拒答并展示人工联系入口。

管理员首次发布助手后，访客可以通过公开聊天页或嵌入个人网站的悬浮入口匿名咨询。事实性回答展示回答级来源列表；负面质量反馈和可靠拒答进入待解决问题队列。管理员可以更新知识来源，新知识版本处理成功后原子替换旧版本，从而形成最小的知识改进闭环。

MVP 不建立独立知识库实体。唯一助手默认使用组织下全部已启用的知识来源。虽然只有一个组织，所有业务数据仍保留真实的组织归属，并通过组织成员关系和 RLS 强制隔离。

## User Stories

### 本地开发与启动

1. 作为开发者，我希望通过明确的前置条件说明安装 Docker、Supabase CLI、Node.js 和 pnpm，以便在新环境中准备开发工具。
2. 作为开发者，我希望通过一个标准命令启动本地 Supabase，以便获得本地 Postgres、Auth 和相关开发服务。
3. 作为开发者，我希望数据库结构全部由版本化迁移创建，以便本地和云端使用同一套结构定义。
4. 作为开发者，我希望重置本地数据库时自动应用全部迁移和种子数据，以便随时恢复可重复的测试基线。
5. 作为开发者，我希望种子数据创建演示组织、唯一管理员关系和默认助手，以便无需手工准备基础数据。
6. 作为开发者，我希望本地环境通过独立环境变量连接本地 Supabase，以便不会误操作 Supabase Cloud。
7. 作为开发者，我希望 DeepSeek 和硅基流动密钥只保存在服务端环境变量中，以便浏览器无法读取供应商凭据。
8. 作为开发者，我希望本地运行完整的后台、公开聊天页和嵌入组件，以便部署前验证真实产品路径。
9. 作为开发者，我希望本地默认可以导入公开网页和手工内容，以便验证完整知识处理链路。
10. 作为开发者，我希望通过仅限开发环境的显式开关导入本机或内网页面，以便测试尚未公开部署的个人网站。
11. 作为开发者，我希望生产环境强制忽略允许私有地址的开发开关，以便本地便利不会削弱线上 SSRF 防护。
12. 作为开发者，我希望本地与云端共享迁移和代码但不复制测试数据，以便生产环境保持干净且可追溯。

### 管理员身份与后台

13. 作为管理员，我希望通过预先配置的邮箱请求 Magic Link，以便无需维护密码也能安全登录。
14. 作为管理员，我希望在本地邮件查看器中获取测试 Magic Link，以便本地开发仍使用真实认证流程。
15. 作为未获授权的人，我希望即使完成 Supabase 认证也无法进入后台，以便组织数据不会因开放认证而暴露。
16. 作为管理员，我希望在概览页看到助手发布状态、可用知识来源数、最近会话数和待处理问题数，以便快速判断系统状态。
17. 作为管理员，我希望后台导航只包含概览、知识来源、助手、会话和待解决问题，以便首版保持清晰。
18. 作为管理员，我希望后台所有业务读取和修改都受组织成员关系约束，以便不会访问其他组织的数据。

### 知识来源导入与生命周期

19. 作为管理员，我希望逐个提交公开网页 URL，以便把个人网站案例页和业务页面转化为可用知识。
20. 作为管理员，我希望手工粘贴内容并填写标题，以便在网页抓取失败或内容尚未发布时仍可维护知识。
21. 作为管理员，我希望手工知识来源可以选择性填写原始 URL，以便有出处时仍能向访客提供可访问引用。
22. 作为管理员，我希望添加知识来源后立即看到“处理中”状态，以便知道系统已经接收请求。
23. 作为管理员，我希望处理成功后看到“可用”状态，以便知道知识已经能够参与回答。
24. 作为管理员，我希望处理失败后看到具体、可理解的失败原因，以便判断是地址、页面内容还是供应商调用问题。
25. 作为管理员，我希望可以重试失败的知识来源，以便临时网络或供应商故障不需要重新填写全部信息。
26. 作为管理员，我希望系统只导入公开的 HTTP 或 HTTPS HTML 页面，以便导入行为保持可预测。
27. 作为管理员，我希望系统提取页面标题和主要正文并去除导航、脚本、样式、表单和页脚噪声，以便检索内容与业务事实相关。
28. 作为管理员，我希望正文过短、过长或无法识别主要内容时得到明确提示，以便不会悄悄生成低质量内容单元。
29. 作为管理员，我希望系统不执行网页 JavaScript，也不绕过登录、验证码、付费墙或反爬限制，以便明确通用爬虫不属于产品承诺。
30. 作为管理员，我希望更新知识来源时旧知识版本继续服务，以便处理中的新版本不会造成线上知识中断。
31. 作为管理员，我希望新知识版本只有在抓取、提取、切分和向量化全部成功后才整体生效，以便回答不会混用不完整版本。
32. 作为管理员，我希望更新失败时旧知识版本保持可用，以便一次失败不会删除当前线上知识。
33. 作为管理员，我希望可以停用知识来源，以便它立即停止参与新回答但以后仍可重新启用。
34. 作为管理员，我希望可以重新启用已停用的知识来源，以便无需重新导入即可恢复使用。
35. 作为管理员，我希望删除知识来源前看到二次确认，以便理解正文、知识版本、内容单元和向量将不可恢复。
36. 作为管理员，我希望删除知识来源后历史会话仍保留当时的引用标题和地址，以便复盘时不会失去回答上下文。

### 助手配置、预览与发布

37. 作为管理员，我希望配置助手名称，以便访客知道正在与哪个服务角色交流。
38. 作为管理员，我希望配置欢迎语，以便访客打开聊天界面时得到明确引导。
39. 作为管理员，我希望配置服务范围说明，以便助手能够解释自己可以处理哪些咨询。
40. 作为管理员，我希望从专业、友好或简洁中选择回答语气，以便表达符合个人网站定位。
41. 作为管理员，我希望配置人工联系入口的文案和 URL，以便可靠拒答后仍有明确下一步。
42. 作为管理员，我希望不能修改可靠性规则、引用规则和安全系统提示词，以便业务配置不会破坏有据回答契约。
43. 作为管理员，我希望不能直接调整模型、召回数量和相关性阈值，以便技术参数由统一测试和服务端配置管理。
44. 作为管理员，我希望在助手发布前通过后台预览提问，以便检查回答、引用和可靠拒答。
45. 作为管理员，我希望首次点击发布后才生成公开访问入口，以便草稿助手不会意外暴露。
46. 作为管理员，我希望复制公开聊天链接，以便分享在线 Demo。
47. 作为管理员，我希望复制嵌入代码，以便把助手加入个人网站。
48. 作为管理员，我希望发布后的配置保存后立即生效，以便首版不需要管理发布版本。
49. 作为管理员，我希望成功处理的新知识版本立即参与已发布助手的后续回答，以便知识更新无需再次发布。
50. 作为管理员，我希望随时下线助手，以便公开聊天页和嵌入入口停止接受新消息。

### 访客咨询体验

51. 作为访客，我希望无需注册、登录或留下联系方式即可开始咨询，以便低摩擦地了解服务和案例。
52. 作为访客，我希望聊天界面明确说明助手是 AI，以便理解回答的性质和限制。
53. 作为访客，我希望输入框旁提示不要提交敏感个人信息，以便降低无意泄露风险。
54. 作为访客，我希望助手的正文以流式方式出现，以便在模型完成前看到响应进展。
55. 作为访客，我希望询问业务事实时获得由现有内容单元支持的有据回答，以便答案不是模型凭空生成。
56. 作为访客，我希望在回答结束后看到不超过三个去重的来源卡片，以便核查答案依据。
57. 作为访客，我希望来源卡片显示页面标题和原始地址并可打开，以便继续浏览相关页面。
58. 作为访客，我希望资料不足时助手明确表示无法确认，以便不会把猜测当成企业承诺。
59. 作为访客，我希望可靠拒答后看到人工联系入口，以便仍能完成下一步咨询。
60. 作为访客，我希望可以继续提出依赖上文的追问，以便不用每轮重复完整背景。
61. 作为访客，我希望每个事实性追问都重新检索知识，以便历史模型回答不会被错误地当成新证据。
62. 作为访客，我希望在当前会话内保留上下文，但新会话不记住我，以便获得连贯体验又不建立长期画像。
63. 作为中文访客，我希望助手使用中文回答，以便自然交流。
64. 作为英文访客，我希望助手使用英文回答，以便在同一知识范围内完成基本英文咨询。
65. 作为使用混合语言或无法识别语言的访客，我希望助手默认使用中文，以便行为保持可预测。
66. 作为访客，我希望可以为每条助手回答选择“有帮助”或“没帮助”，以便向管理员表达质量判断。
67. 作为访客，我希望技术故障时看到“服务暂时不可用”而不是知识不足拒答，以便区分系统问题与无答案。
68. 作为访客，我希望失败的回答可以重试，以便临时供应商故障不会终止咨询。
69. 作为访客，我希望达到会话问题上限时能够开始新会话，以便限制成本的同时继续使用服务。
70. 作为访客，我希望达到全局每日预算后仍能看到人工联系入口，以便 AI 暂停时仍有可用路径。

### 公开聊天页与嵌入体验

71. 作为访客，我希望通过公开链接直接使用助手，以便无需先访问宿主网站。
72. 作为网站访客，我希望通过页面右下角的悬浮入口打开助手，以便在浏览内容时随时咨询。
73. 作为网站所有者，我希望嵌入聊天使用 iframe 隔离样式，以便不会破坏宿主网站布局。
74. 作为网站所有者，我希望悬浮入口不遮挡网站主体内容和直接联系方式，以便 AI 不是访问业务信息的唯一入口。
75. 作为开发者，我希望公开助手 ID 只用作定位标识而不是密钥，以便安全设计不依赖隐藏客户端值。
76. 作为开发者，我希望公开聊天只能通过服务端接口访问业务数据，以便浏览器不能绕过校验直接读取 Supabase 表。

### 会话复盘与改进闭环

77. 作为管理员，我希望查看最近 30 天的会话列表，以便了解访客真实咨询内容。
78. 作为管理员，我希望查看单个会话的消息、引用、质量反馈和系统错误，以便复盘回答结果。
79. 作为管理员，我希望可靠拒答自动创建待解决问题，以便知识不足不会被遗漏。
80. 作为管理员，我希望“没帮助”的质量反馈自动创建待解决问题，以便低质量回答进入改进队列。
81. 作为管理员，我希望待解决问题保留原始提问、回答、引用和会话入口，以便理解问题上下文。
82. 作为管理员，我希望按“待处理”和“已解决”查看待解决问题，以便管理最小处理流程。
83. 作为管理员，我希望补充或更新知识来源后手动标记问题为已解决，以便完成一次清晰的改进闭环。
84. 作为管理员，我希望技术供应商故障不会创建待解决问题，以便知识队列不被基础设施错误污染。
85. 作为管理员，我希望可以删除单个会话，并同时删除消息、质量反馈和关联待解决问题，以便主动清除访客数据。
86. 作为管理员，我希望过期会话及关联数据在 30 天后自动删除，以便匿名咨询数据不会无限期保留。

### 安全、隔离与成本

87. 作为组织所有者，我希望所有助手、知识来源、知识版本、内容单元、会话和待解决问题都有组织归属，以便未来扩展时不会混用数据。
88. 作为组织所有者，我希望后台访问由组织成员关系和 RLS 双重约束，以便单组织 MVP 也能真实验证隔离。
89. 作为组织所有者，我希望公开接口只能从已验证的助手推导组织，以便访客不能伪造组织标识越权查询。
90. 作为安全维护者，我希望 URL 导入拒绝本机、内网、保留地址和云元数据地址，以便防止 SSRF。
91. 作为安全维护者，我希望抓取限制重定向、响应时间、响应体积和内容类型，以便恶意页面不能无限消耗资源。
92. 作为安全维护者，我希望访客输入和知识来源都被视为不可信内容，以便来源中的指令不能改变系统规则。
93. 作为安全维护者，我希望助手拒绝泄露系统提示词、内部内容单元、密钥和其他会话，以便减少提示词注入风险。
94. 作为安全维护者，我希望回答只渲染受控 Markdown，不执行原始 HTML、脚本、iframe 或图片，以便防止内容注入。
95. 作为安全维护者，我希望模型生成的任意 URL 不被当作可信引用，以便只有服务端引用快照能够生成来源链接。
96. 作为项目维护者，我希望每个会话同一时间只允许一个回答请求，以便避免并发重复计费。
97. 作为项目维护者，我希望每个会话每分钟最多发送五条消息，以便限制短时间滥用。
98. 作为项目维护者，我希望每个会话最多提出三十个问题，以便控制单个匿名会话成本。
99. 作为项目维护者，我希望应用有可配置的全局每日消息预算，以便公开 Demo 不会产生失控费用。
100. 作为项目维护者，我希望调用日志记录模型、Token、耗时、状态、错误类型和追踪 ID，以便分析成本与故障。
101. 作为访客，我希望调用日志不保存完整提示词和回答正文，也不保存 IP 画像，以便减少额外隐私数据。

### 质量保证与部署

102. 作为开发者，我希望确定性测试使用固定 HTML 和模拟模型响应，以便不消耗额度也能稳定验证核心行为。
103. 作为开发者，我希望浏览器测试覆盖登录、导入、预览、发布、公开问答和引用，以便验证最高层业务闭环。
104. 作为开发者，我希望真实 AI 冒烟测试调用完整 Embedding、Rerank 和 DeepSeek 链路，以便确认本地真实集成可用。
105. 作为开发者，我希望真实 AI 冒烟测试通过独立命令按需运行，以便普通 CI 不受模型波动和额度影响。
106. 作为开发者，我希望至少十个应答问题和十个拒答问题组成离线评测集，以便校准召回、重排和拒答阈值。
107. 作为开发者，我希望每个应答问题标注预期知识来源，以便测试引用是否来自正确页面。
108. 作为开发者，我希望少量英文问题进入评测集，以便验证双语言问答边界。
109. 作为项目维护者，我希望所有本地测试通过后再链接 Supabase Cloud，以便云端部署基于已验证迁移。
110. 作为项目维护者，我希望云端只接收迁移、配置和必要种子数据，以便本地测试会话与知识不会进入生产。
111. 作为项目维护者，我希望 Next.js 部署到 Vercel，数据、认证和向量检索部署到 Supabase Cloud，以便快速获得可公开访问的作品集 Demo。
112. 作为第三方开发者，我希望 README 清楚说明本地启动、环境变量、迁移、种子、测试和部署流程，以便能够理解并运行开源项目。

## Implementation Decisions

### 产品范围与领域边界

- MVP 是“单组织、单管理员、单助手、多个知识来源”的完整纵向闭环。
- MVP 不建立独立知识库实体。知识来源直接属于组织，唯一助手默认使用全部已启用的知识来源；该决定遵守 ADR-0002。
- 组织是业务数据隔离边界。即使 MVP 只有一个组织，也必须通过组织成员关系和 RLS 实施隔离；该决定遵守 ADR-0003。
- 访客无需账户。会话通过匿名标识维持当前会话上下文，不创建访客画像或跨会话记忆。
- 管理员是唯一受权维护知识来源、配置助手、复盘会话和处理待解决问题的角色。

### 应用与部署架构

- 使用 Next.js 16 App Router、TypeScript 和 pnpm 构建单体全栈应用。
- React Server Components 负责后台页面的默认读取路径。
- Server Actions 处理受认证保护的后台表单修改。
- Route Handlers 处理 URL 导入、公开聊天接口、流式回答和嵌入相关公共资源。
- 服务端使用 Node.js Runtime，以支持 HTML 解析；MVP 不使用 Edge Runtime。
- 使用 Tailwind CSS 与 shadcn/ui 构建管理后台、公开聊天页和嵌入聊天界面。
- 使用 `@supabase/ssr` 与 `@supabase/supabase-js` 完成认证和数据访问。
- 数据结构由 Supabase SQL 迁移管理，不引入 Prisma 或 Drizzle。
- 使用 Vercel AI SDK 6 的 OpenAI-compatible provider 调用 DeepSeek 并处理流式文本。
- 硅基流动 Embedding 和 Rerank 通过独立轻量适配器调用，使模型名称、地址、密钥、超时和阈值保持服务端可配置。
- 不引入 LangChain、LlamaIndex、独立后端、独立 Worker 或 monorepo。
- 开发阶段使用本地 Supabase；验收通过后，Next.js 部署到 Vercel，数据库、认证与 `pgvector` 部署到 Supabase Cloud。

### 本地 Supabase 工作流

- Docker 与 Supabase CLI 是本地开发前置条件。
- 本地环境必须通过标准 Supabase CLI 流程启动、停止和重置。
- 所有数据库结构变化必须先形成迁移并在本地重置验证，不能只在 Supabase Studio 中手工修改。
- 种子数据创建演示组织、管理员成员关系和默认草稿助手，并提供可用于测试的示例知识。
- 本地 Supabase Auth 使用本地邮件查看器完成 Magic Link，不增加认证绕过模式。
- 本地和云端使用完全独立的环境变量、Supabase 密钥、模型密钥和管理员邮箱。
- 上云只部署迁移、配置与必要种子，不迁移本地业务数据。
- 本地运行依赖网络和真实模型 API；MVP 不承诺完全离线的模型推理。

### 管理员认证与访问

- 只允许一个预配置管理员邮箱登录，不提供公开注册。
- 完成 Supabase 认证不等于获得后台权限；服务端还必须确认该身份属于当前组织。
- 后台包含登录、概览、知识来源、助手、会话和待解决问题六个入口。
- `service_role` Key 仅在服务端可用，禁止使用任何公开环境变量前缀暴露。

### 助手配置与发布

- 助手只开放五项业务配置：名称、欢迎语、服务范围说明、回答语气、人工联系入口文案与 URL。
- 回答语气只提供专业、友好和简洁三个预设。
- 可靠性规则、引用规则、安全规则、模型、召回数量、重排数量和阈值不作为管理员配置。
- 助手初始为草稿，只能后台预览。
- 首次发布后生成公开聊天入口和嵌入入口。
- 发布后配置保存即生效，成功处理的新知识版本立即参与回答；MVP 不保存发布快照或配置版本。
- 下线助手后，公开入口停止接受新消息，但保留后台历史数据。

### 知识来源与处理状态

- 知识来源支持两种类型：单个公开网页 URL 和手工内容。
- URL 来源保存原始地址与提取标题；手工来源要求标题，原始地址可选。
- URL 导入只接受公开 HTTP 或 HTTPS HTML，不执行 JavaScript，不处理登录、验证码、付费墙、文件、图片、附件、评论区或站外链接。
- 抓取必须限制协议、地址范围、DNS 解析结果、重定向、超时、响应体积和内容类型，并拒绝本机、内网、保留地址及云元数据地址。
- 本地开发可通过显式开发开关允许私有来源地址；该能力必须同时受开发环境判断约束，不能只依赖环境变量值，生产环境强制禁用。
- 页面处理提取标题与主要正文，去除导航、脚本、样式、表单、页脚等噪声。
- 内容按标题和段落边界形成内容单元。正文长度、内容单元大小、重叠和批量大小由服务端配置与离线评测调节，不作为产品配置。
- 处理采用同步服务端请求，但每一步都持久化为可观察状态。至少区分处理中、可用和失败。
- 失败状态保存安全、可理解的原因并允许管理员重试。
- 不引入队列或独立 Worker；整站抓取、文件处理等长任务出现后再升级为异步处理。

### 知识版本、停用与删除

- 每次完整处理生成新的知识版本以及其内容单元。
- 更新时当前可用知识版本继续参与回答，新版本全部成功后原子切换；该决定遵守 ADR-0001。
- 新版本失败时保留旧知识版本，不允许部分内容单元生效。
- 同一知识来源在任一时刻只有一个知识版本可用于回答。
- 停用保留知识来源及内容，但立即停止参与新回答；重新启用后恢复当前可用版本。
- 删除不可恢复地移除知识来源正文、知识版本、内容单元和向量，并要求二次确认。
- 回答生成时保存引用快照，包括当时的标题和地址。删除知识来源不删除仍在保留期内的历史会话与引用快照。

### 检索增强生成链路

- 硅基流动 `BAAI/bge-m3` 为内容单元和访客问题生成向量。
- 向量存储和相似度召回使用 Supabase Postgres `pgvector`。
- 初始基线从向量检索召回约二十个候选内容单元，再由 `BAAI/bge-reranker-v2-m3` 重排并保留约五个高相关内容单元。
- 候选数量、最终数量和阈值必须通过离线评测校准，并以服务端配置保存，不硬编码为单个问题规则。
- DeepSeek 使用 `deepseek-v4-flash` 的非思考模式生成回答；模型名称必须可通过服务端配置替换。
- 每个事实性问题和追问都重新执行检索。历史消息只用于消解指代、理解追问和组织表达，之前的助手回答不能成为事实证据。
- DeepSeek 接口是无状态的，服务端只传递当前会话所需的有限近期消息，不建立跨会话长期记忆。
- 首版不使用 Agent、工具调用或思考模型。

### 回答、引用与可靠拒答契约

- 寒暄、身份说明等非事实内容可以不附引用。
- 业务事实只有在证据集达到相关性门槛时才能形成有据回答。
- 模型可以总结和改写证据，但不能加入证据中不存在的事实。
- 证据不足时必须可靠拒答并展示人工联系入口，不能让模型用常识补全。
- 访客界面不展示置信度百分比。
- 引用采用回答级来源列表，不做句子级脚注或原文高亮。
- 最终证据集按知识来源去重，最多展示三个来源。
- 引用标题和 URL 只能由服务端根据知识来源生成，模型输出的 URL 不构成引用。
- 流式正文完成后展示完整来源列表。
- 受控 Markdown 渲染禁止原始 HTML、脚本、iframe 和图片。

### 匿名会话与公开接口

- 访客无需账户、姓名、邮箱或电话即可咨询。
- 浏览器获得匿名会话标识，服务端以此维持一个助手内的连续会话。
- 会话内支持有限多轮上下文；会话间不共享记忆。
- 公开助手 ID 是可见标识，不是安全凭据。
- 公开接口不能接受客户端提供的组织 ID；必须先验证已发布助手，再由助手推导组织。
- 公开聊天只通过 Next.js 服务端访问数据，Supabase 匿名角色不得直接读取业务表。
- 公开聊天页与嵌入聊天共用相同的助手、会话、限流和回答链路。

### 发布与嵌入

- 发布后提供一个可直接访问的公开聊天页。
- 同时提供可复制的嵌入代码，在宿主网站显示悬浮入口，并通过 iframe 加载聊天界面。
- iframe 隔离宿主网站与聊天界面的样式和脚本。
- 悬浮入口不得遮挡主体内容或直接联系方式。
- MVP 不提供 React SDK、npm 包、公开开发者 API、自定义域名或复杂品牌主题。

### 质量反馈与待解决问题

- 每条助手回答最多接受一条“有帮助”或“没帮助”的质量反馈。
- 可靠拒答自动创建待解决问题。
- “没帮助”自动创建待解决问题；重复反馈不得创建重复条目。
- 技术故障不属于可靠拒答，不创建待解决问题。
- 待解决问题至少包含原始问题、对应回答、引用、会话关联以及待处理或已解决状态。
- 管理员补充或更新知识来源后，手动将待解决问题标记为已解决。
- MVP 不做文本评价、自动聚类、负责人分配、自动生成知识或自动形成后台评测集。

### 限流、预算与调用日志

- 一个会话同一时间只允许一个有效回答请求。
- 一个会话每分钟最多发送五条消息。
- 一个会话最多提出三十个问题，之后引导开始新会话。
- 应用提供服务端全局每日消息预算；超出后停止模型调用并显示人工联系入口。
- 所有限制都由服务端校验，客户端计数只用于提前改善提示。
- 限流依据会话消息与当日调用日志计算，不建立订阅、套餐或精确计费系统。
- 调用日志保存供应商、模型、Token、耗时、成功状态、错误类型和追踪 ID。
- 调用日志不保存完整提示词、回答正文、API Key 或 IP 画像。

### 供应商故障处理

- Embedding 失败使知识来源进入失败状态，并允许手动重试。
- Rerank 失败时不绕过重排生成回答，而是返回服务暂时不可用。
- DeepSeek 失败或超时时保留访客问题，返回服务暂时不可用并允许重试。
- 供应商限流可采用短暂退避后最多自动重试一次。
- MVP 不自动切换备用模型或供应商。
- 管理后台必须区分知识不足、输入被拒绝、限流和供应商故障。

### 数据模型

- `organizations` 保存组织。
- `organization_members` 保存管理员与组织的授权关系。
- `assistants` 保存唯一助手配置、草稿或已发布状态以及公开 ID。
- `knowledge_sources` 保存 URL 或手工知识来源、生命周期状态和当前可用知识版本关系。
- `knowledge_revisions` 保存一次完整处理结果和处理状态。
- `content_units` 保存可检索正文、顺序、来源关系、知识版本关系和向量。
- `conversations` 保存助手、组织、匿名会话信息和生命周期时间。
- `messages` 保存访客与助手消息、消息类型和生成状态。
- `citations` 保存回答生成时的来源标题和地址快照，以及必要的来源关系。
- `quality_feedback` 保存一条回答的有帮助或没帮助评价。
- `unresolved_questions` 保存因可靠拒答或负面反馈产生的待处理事项。
- `ai_call_logs` 保存调用类型、供应商、模型、Token、耗时、结果和安全错误元数据。
- 业务表按需要包含组织 ID，并建立防止跨组织引用的约束或服务端验证。
- 数据库必须启用 `pgvector` 和 30 天清理所需的定时任务能力。

### 数据保留

- 匿名会话、消息、质量反馈和关联待解决问题默认保留三十天。
- 数据库定时任务每天清理过期会话，并级联删除消息、反馈和关联待解决问题。
- 管理员可以提前删除单个会话，使用同样的级联语义。
- 引用快照随会话保留并随会话删除。
- 模型调用日志采用不含正文的最小记录；具体保留期不得长于业务排障和成本核对的合理需要，并在部署配置中明确。
- 聊天输入区域展示不要提交敏感个人信息的提示。

### 语言

- 管理后台与聊天组件 UI 只提供简体中文。
- 知识来源允许中文或英文。
- 助手按访客当前问题语言使用中文或英文回答；混合或无法识别时默认中文。
- 两种回答语言遵守完全相同的检索、引用和可靠拒答契约。
- MVP 不建设通用国际化框架或其他语言质量承诺。

### 实现顺序

1. 建立工程、本地 Supabase、迁移、种子、管理员登录和基础 CI。
2. 实现 URL 与手工导入、处理状态、知识版本、内容单元和向量写入。
3. 实现向量召回、重排、DeepSeek 流式回答、引用、可靠拒答和后台预览。
4. 实现匿名会话、公开聊天页、悬浮嵌入、发布或下线和服务端限流。
5. 实现会话复盘、质量反馈、待解决问题、知识更新和引用快照。
6. 完成 RLS、SSRF、提示词注入、保留清理、真实 AI 冒烟测试、文档和云端部署。

## Testing Decisions

### 测试原则与接缝

- 测试只断言用户或外部调用者能够观察到的行为，不断言 React 内部状态、私有函数调用次数或 SQL 实现细节。
- 主要测试接缝是一条浏览器级完整闭环：管理员登录、导入知识来源、等待可用、后台预览、发布助手、打开公开聊天页、获得有据回答并打开引用。它是最高层、最能代表 MVP 是否成立的单一接缝。
- 由于仓库当前没有应用代码或既有测试，没有可复用的 prior art。新增测试应优先围绕上述浏览器接缝组织，只有网络安全、数据库隔离、文本处理和供应商波动无法在该接缝中稳定定位时才增加更低层测试。
- 确定性自动测试不得依赖真实模型供应商；真实供应商集成由独立冒烟测试负责。

### 浏览器端到端测试

- 使用 Playwright 对本地 Next.js 和本地 Supabase 执行完整闭环。
- 测试通过本地邮件查看器取得 Magic Link，不绕过管理员认证。
- 主闭环使用固定网页内容和可预测的供应商替身，验证导入状态、预览、发布、匿名提问、流式回答结束状态和来源列表。
- 补充端到端场景覆盖可靠拒答、负面反馈生成待解决问题、助手下线、删除会话和嵌入入口。
- 端到端测试应通过可访问角色、标签和可见文案操作界面，避免依赖脆弱 DOM 结构。

### 本地 Supabase 集成测试

- 从空数据库执行全部迁移和种子，证明环境可重建。
- 验证预配置管理员可以访问组织数据，已认证但未加入组织的用户无法访问。
- 验证公开匿名角色无法直接读取助手配置、知识来源、内容单元、会话和调用日志。
- 验证跨组织读取和写入被 RLS 或约束拒绝，即使测试种子临时创建第二组织。
- 验证知识版本原子切换：新版本成功前旧版本仍可用，失败版本永不参与检索。
- 验证停用、重新启用、删除、引用快照和会话级联删除语义。
- 验证三十天清理只删除过期会话及关联数据，不影响仍在保留期内的数据。

### 确定性服务测试

- URL 安全测试覆盖本机、私网、保留地址、云元数据地址、DNS 解析变化、重定向链、非 HTML、超时和超大响应。
- 正文提取测试使用固定 HTML，验证主体正文保留而导航、脚本、样式、表单和页脚被移除。
- 内容单元测试断言标题和段落语义不会无故丢失，不绑定具体内部函数。
- 供应商适配器使用模拟 HTTP 响应验证成功、超时、限流、无效响应、一次重试和追踪 ID。
- 检索链路使用固定向量与重排结果验证候选过滤、来源去重、最多三个引用以及门槛以下可靠拒答。
- 回答渲染测试覆盖恶意 Markdown、原始 HTML、脚本、iframe、图片和模型伪造 URL。
- 会话测试覆盖有限多轮追问、无跨会话记忆、单请求并发限制、每分钟限制、三十问题上限和全局每日预算。
- 反馈测试覆盖每条回答的唯一评价、可靠拒答自动建单、负面反馈自动建单以及技术故障不建单。

### 离线评测

- 评测集至少包含十个基于示例知识可回答的问题和十个应可靠拒答的问题。
- 每个可回答问题标注一个或多个预期知识来源。
- 评测同时检查是否回答、是否引用预期来源、是否包含来源外事实以及是否错误拒答。
- 评测包含少量英文问题，但不扩展为通用多语言基准。
- 召回数量、重排数量和相关性阈值只能基于整组结果调整，不能为单个问题添加例外。
- 评测集属于开发测试资产，不成为管理员可编辑的产品功能。

### 真实 AI 冒烟测试

- 提供独立命令，使用真实硅基流动 Embedding、Rerank 和 DeepSeek API。

## Further Notes

- 本规格是完整产品方案的第一阶段，不替代长期产品愿景。长期方向仍可加入多知识库、多助手、多组织界面、业务动作、评测和运营分析。
- MVP 的首个演示组织是个人网站 AI 售前顾问。示例知识应优先来自真实、可公开访问的个人网站案例页，且不得虚构经验、客户、报价或成果。
- `deepseek-v4-flash`、`BAAI/bge-m3` 和 `BAAI/bge-reranker-v2-m3` 是 2026-07-27 确认的初始模型。模型名称必须保持服务端可配置，以应对供应商上下线或价格变化。
- 免费模型不等于无限额度或永久免费。全局预算、调用日志、失败关闭和部署前真实冒烟测试都是正式交付内容。
- 可靠拒答和技术故障是不同结果：前者表示现有知识不足并进入改进闭环，后者表示系统暂时无法完成处理且不应污染待解决问题队列。
- 本规格遵守领域词汇表中的“组织、知识来源、知识版本、内容单元、有据回答、引用、可靠拒答、访客、会话、管理员、助手、质量反馈和待解决问题”定义。
- 实现必须遵守三项现有 ADR：知识来源更新原子切换、MVP 不建立知识库实体、单组织 MVP 仍强制组织数据边界。
- 建议在实现阶段按六个纵向阶段分别拆分工单；本次 `to-spec` 仅发布规格，不自动创建实现工单。
